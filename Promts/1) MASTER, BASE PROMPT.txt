You are helping me build "PG360", a multi-tenant PG / Hostel Management SaaS for the Indian market.
Owners pay a yearly subscription. The platform owner (me) onboards PG owners.

## Product in one line
A web app where PG owners manage rooms, tenants, rent, food, complaints and P&L — and each
tenant gets their own login to see their room (incl. WiFi password), bill, and raise issues.

## Roles (strict top-down hierarchy)
- super_admin  -> ME, the platform owner. Creates PG owner accounts. Sees the whole platform.
- admin        -> PG owner. Created by super_admin. Manages ONE pg.
- staff        -> manager/warden/cleaner. Created by an admin. Scoped to that admin's pg.
- tenant       -> inmate. Created by admin/staff. Read-mostly access to their own data only.

Everything is created top-down: super_admin -> admin -> staff/tenant.

## Tech stack (do not deviate without asking)
- Next.js (App Router) + TypeScript (strict) + Tailwind CSS for the web app.
- Supabase for Postgres DB, Auth, Storage, Realtime. Supabase IS the backend.
- Custom logic: Next.js Server Actions and Supabase Edge Functions. NO separate Angular/Express server.
- Hosting: Vercel. Email: Supabase auth emails now; MSG91/Resend for notifications later.
- Mobile (React Native / Expo) comes in Phase 3 and reuses this same Supabase backend.

## Architecture principles (CRITICAL — follow on every table and query)
1. MULTI-TENANCY: almost every row belongs to a PG. Add `pg_id` to every PG-scoped table.
2. ROW LEVEL SECURITY (RLS): enable RLS on EVERY table. No table ships without policies.
   - A profile table maps each auth user to {role, pg_id}.
   - admins/staff can only touch rows where pg_id = their pg_id.
   - tenants can only touch rows that belong to them (tenant_id = their id) or read-only pg data
     explicitly meant for them (their room, food menu, their invoices).
   - super_admin can manage pg_accounts and read platform-wide aggregates.
3. AUTH: Supabase Auth. On signup/creation, insert a row into `profiles` with role + pg_id.
   Resolve role/pg_id from `profiles` in policies and in the UI (never trust the client).
4. NEVER hardcode secrets. Use .env.local locally and Vercel/Supabase env vars in prod.
5. Use Supabase migrations (SQL files) for ALL schema changes — never click-ops only.

## Repo conventions
- App Router with route groups: (marketing) for landing, (super-admin), (admin), (tenant).
- `/lib/supabase/` for typed server + browser clients. Generate DB types from Supabase.
- Server Actions for mutations; RLS is the real security boundary, not the UI.
- Reusable UI in `/components/ui`. Keep forms accessible and mobile-friendly.
- Tailwind only; no heavy UI kit required. Clean, dense, dashboard-style layouts.
- Money in paise/integer or numeric(12,2); never floats for currency. Dates in ISO. Timezone Asia/Kolkata.
